## Shared decisions and contracts

The first account method is email and password, with email confirmation, password recovery and sign-out. This keeps future external-provider sign-in outside the current work. Use the hosted provider's default email templates initially. Callback handling accepts a one-time `code`, exchanges it for a session, and permits only local return paths. If the provider's current confirmation flow needs a different callback, resolve that against current documentation during stage 1 before coding the form; do not turn off email confirmation to bypass it.

Store all mileage internally as kilometres, rounded to three decimal places after a miles conversion; display the user's km/mi preference. Store the job date as a calendar date, not a UTC timestamp. A bike may have unknown mileage. Logging or starting a job requires mileage; historical entries never reduce the latest known mileage. Corrections to the bike's mileage are explicit detail edits.

Use three private tables plus custom templates: `garage_bikes`, `maintenance_jobs`, `garage_files`, `maintenance_templates`. Jobs contain a JSON checklist snapshot. Each snapshot task has its own ID, optional stable template task key, action, label, state, reason, current notes, completion timestamp, and optional origin linking to an earlier job/task. A job row has a revision number for conflict detection. Do not split each checkbox save into separate task and job updates.

Generated database types remain the source for stored row types. Stage 2 introduces these application contracts in `src/lib/maintenance/types.ts`:

```ts
export type TaskState = 'todo' | 'done' | 'skipped' | 'not_applicable'
export type TaskAction = 'inspect' | 'clean' | 'adjust' | 'replace' | 'other'
export type JobStatus = 'in_progress' | 'completed' | 'partial'
export type CloseReason = 'all_done' | 'manual' | null
export type Origin = { jobId: string; taskId: string; previousNotes: string }
export type JobTask = {
  id: string; key: string | null; label: string; action: TaskAction;
  state: TaskState; reason: string; notes: string; doneAt: string | null;
  origin: Origin | null; reference: string | null; warning: string | null;
  specification: string | null; safety: 'green' | 'yellow' | 'red' | null;
}
export type TemplateTask = Pick<JobTask,
  'key' | 'label' | 'action' | 'reference' | 'warning' | 'specification' | 'safety'>
export type Template = {
  id: string; version: number; title: string;
  kind: 'scheduled' | 'time_based' | 'individual' | 'custom';
  motorcycleId: string | null; years: number[]; markets: string[];
  variants: string[]; intervalKm: number | null; intervalMonths: number | null;
  frequency: 'once' | 'recurring' | 'on_demand';
  source: string | null; tasks: TemplateTask[];
}
export type JobDraft = {
  id: string; bikeId: string; title: string; date: string; mileageKm: number;
  template: Template | null; tasks: JobTask[]; notes: string;
  parts: string; performer: string; costMinor: number | null; currency: string | null;
}
export type JobView = JobDraft & {
  revision: number; status: JobStatus; closeReason: CloseReason;
  closedAt: string | null; createdAt: string;
}
export type TaskPatch = Partial<Pick<JobTask, 'state' | 'reason' | 'notes'>>
export type SavedResult<T> =
  | { ok: true; value: T }
  | { ok: false; error: 'invalid' | 'not_found' | 'conflict' | 'save_failed'; message: string; current?: T }
```

Limits: nickname 80 characters; make/model/variant/market 120 each; registration 40; job/task title 160; job notes/parts/per-task notes 4,000; performer 120; task reason 500; at most 100 tasks per job/template. Stored mileage must be finite and nonnegative. Zero is valid. Template versions are positive integers; empty templates are rejected.

Costs use nonnegative integer minor units, not floating-point storage. Require a three-letter currency when a cost is supplied; blank cost means null and a zero cost is valid. Support EUR, GBP and USD in the initial selector. Do not calculate totals across different currencies.

Uploads: bike photos JPEG/PNG/WebP, at most 10 MiB and 40 million decoded pixels, converted server-side to metadata-free WebP with a 1,600 px longest edge. Receipts accept those images or PDF, at most 10 MiB per file and 10 receipts per job. Never render a PDF inside the app's DOM; offer a private download. Do not accept SVG/HTML as photographs or receipts. Keep filenames only as text and use generated storage names. Signed URLs last 60 seconds and are refreshed when required; never store them as the record's image path.

Closure: an active job automatically completes only when its nonempty checklist is entirely Done. A manually closed job stays closed; its label becomes partial when applicable tasks remain unfinished/skipped. A recorded Not applicable reason allows manual completion without that task being Done. Editing an automatically closed job back to unfinished reopens it. Editing notes alone never changes closure. This resolves the spec's untick behaviour without silently reopening a manually closed activity.

"Previous activity" means the most recently created existing activity for that bike, ordered by `created_at`, then ID; it excludes the new draft. Carry-over never reaches back through multiple older jobs. Preserve source task states and notes. A single database transaction creates the new activity and, if explicitly selected, closes the previous activity. Stable IDs make retrying that transaction safe.
